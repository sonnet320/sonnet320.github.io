## 作業の進め方

- 変更はブランチを作って Pull Request にし、そねっとさんが確認して Merge します。main に直接 push しません。
- 価格の調査は GPT、反映は Claude。GPT の価格CSVは、そねっとさんがチャットで Claude に渡し、Claude が手元で変換して(載せない店舗の行を消してから)PR にします。生のCSVをリポジトリに直接置かないでください(手順は `data/incoming/README.md`)。
- ファン・クーラーなど製品の追加はシートへの反映が前提なので Claude が担当します。
- おすすめBTOの追加は README.md の「構成を追加するとき」の手順どおりに行います。
- シートの温度の計算(`DIAG_VER`)を変えた PR では、掲載中のおすすめBTOの計算結果も計算し直し、`modelVersion` をそろえます。2D の書き出しは、クラウド側の headless Chromium で `pc-sheet/?preset=構成ID` を開き、`PCSheet.computeResult()` を呼べば作れます(作者のPCは不要)。
- シートに部品(CPU・グラボ・クーラー・ファン・ケース)を追加したら `python tools/make_price_map.py` を実行し、`data/price_map.json` を更新します。

## GPU 温度のモデル(2026-10-13、sheet-v60-gpu3d)

- 基準は作者のPCの実測(2026-10-02、`_dev/validation/user_pc_calibration_20261002.md`)。RTX 5080 は k=1.0 のまま。モデルを変えたら、この構成で 2D・3D とも実測 63.6°C に近いか(±2.5°C)を必ず確認する
- 2D は、温まった空気の吸い込みと、グラボに届く風量の見積もりを補正している(`gpuIntake`、`GPU_2D_MIX`)。3D の計算方法は変えていない
- チップごとの補正 k は、hwcooling.net のテスト機を 3D で再現した結果で決めた(`gpu_2d3d_20261013.md`)
- GPU の3D計算は、作者のPCの内蔵ブラウザで公開中のシートを一時的に読み込み、内部の関数を呼んで実行した(クラウド側は GPU がなく、3D は非常に遅い)
- ファン口径(`GPU_FAN_D`)とベイパーチャンバーの印は、GPT の調査資料から数値と出典だけを取り出して登録(`gpu_fan_diameter_20261013.md`)。資料の ZIP は公開しない

## GPU ファンの最大回転数(2026-10-13、gpu-fan-maxrpm)

- `pc-sheet/index.html` の `GPU_FAN_MAX` に、42枚のファン最大回転数(100%時のレビュー実測)を登録。出典は `_dev/validation/gpu_fan_maxrpm_20261013.md`
- グラフィックボード欄に「ファンの最大回転数」の入力欄を追加。入力値はカードごとに `state.gpuRpm`(カスタムは `gpuCustom.rpm`)に保存され、登録値より優先される
- ファンの%の横に「約○rpm」を表示し、手動のときは回転数でも指定できる。温度の計算には使っていない(回転数を入れても誤差が縮まなかったため)
- 消費電力は温度に反映済み。カードの `power`(空なら GPU の標準値)× GPU使用率が発熱になり、グラボ温度とケース内の空気の計算の両方に入る

## CPU 温度の場面ごとの上乗せ(2026-10-14、sheet-v61-cpu)

- 作者のPCの実測(OCCT・Cinebench・ゲーム3場面・アイドル)で、全コアの重い処理は合っていた。ゲームは同じ電力でも約3°C 高く、アイドルは Tctl が高めに出る
- CPU の負荷に「FPS(高フレームレート)」を追加。Ryzen 9000 だけ、ゲーム・FPS に +3°C、アイドルに近い負荷に最大 +10°C を足す(`cpuExtra`、`CPU_HOT_ADD`、`CPU_IDLE_ADD`)
- 3D でラジエーターファンが遅いときの風量を 2D にそろえる補正(`CPU_RAD3D`)
- 記録:`_dev/validation/cpu_temp_game_20261014.md`、`_dev/validation/user_pc_cinebench_20261014.md`(PR #28)
- ほかの CPU への適用は、GPT の調査結果と視聴者のログを見てから(Intel は v62 で別の補正を入れた。下記)
- アイドルの上乗せは負荷の2乗で減るが、ゲーム(9800X3D で約82W)でもまだ約3°C 残る。ゲームの上乗せと合わせると、Ryzen 9000 のゲームは v60 より約 +6°C
- ケースの欄に「オープンフレーム(ケースなし)」を追加。開放ベンチのレビューと直接比べるため。部品は室温に近い空気を吸うとして、2D・3D とも同じ式で温度を出す(`state.openFrame`、`OPEN_CPU_RISE` など)

## Intel CPU を高めに推定する補正(2026-10-14、sheet-v62-intel)

そねっとさんの判断:「Intel は外れが大きいので、温度を高めにする前提で調整する。欠けているデータは推測で埋める」。画面にも「推定」と表示する。

- CPU 側の熱の通りにくさを、Core 第12〜14世代は 1.3倍、Core Ultra は 1.1倍(`cpuRpK`)
- Intel のゲーム・FPS に +8°C(`INTEL_HOT_ADD`)。アイドルの上乗せは、データがないため入れていない
- 空冷(シングル・デュアルタワー)は、発熱がクーラーの冷却性能の85% を超えると熱の通りにくさを増やす(`towerSat`)。簡易水冷・トップフローは変えていない
- 2D と 3D の差は、上限で頭打ちになる構成を除いて1°C 前後
- データが増えたら(特に視聴者の HWiNFO のログ)倍率と上乗せを見直す。今は「低く出すより高く出す」側に寄せている
- 記録:`_dev/validation/cpu_intel_estimate_20261014.md`

## VRM の計算の見直し(2026-10-26、sheet-v64-vrm → sheet-v65-vrm2d)

- VRM の熱の通りにくさを、ヒートシンクの大きさ(なし・小・中・大・特大)から出す形にした。チップセットごとの標準の大きさを AMD・Intel 別の表(`VRM_CHIPSETS`)で決め、シートの「VRMのヒートシンク」で変えられる(`state.vrmHs`)
- VRM の発熱を、CPU 用のフェーズ数と部品の定格から計算する形にした(`vrmLoss`。空欄ならヒートシンクの大きさごとの一般的な構成)。CPU の電力はコア・SoC・そのほかに分け、SoC などの電力は CPU の種類ごと(`cpuRails`。AM5 は作者の 9700X の実測、ほかは仮定)。CPU から基板を伝わる熱 `VRM_SOCK`(CPU 1W あたり 0.18°C)を足し、作者のPCの実測(OCCT Power で 44.7°C、X870 Taichi Creator は 18+2+1 フェーズ・特大のヒートシンク)に合わせた
- 掲載中のおすすめBTOは VRM が多くの構成で +4〜+8°C(2D で再計算済み)。データは作者のPCの1点だけ。記録:`_dev/validation/vrm_heatsink_20261026.md`
- 2D と 3D の比較(作者のPC、`_dev/vrm3d.html`)で VRM の差は ±1.3°C。OCCT Power は 3D 46.0°C(実測 44.7)。ソケットの熱は 2D の誤差の埋め合わせではなく、3D でも必要
- 作者のPCの Cinebench・ゲームの VRM の実測(10/14 の HWiNFO)で、シートとの差は −2.4〜+4.3°C。VRM の上昇はほとんどが基板から伝わる熱(電流一定の MISC 用 VRM も同じだけ上がる)で、`VRM_SOCK` 0.18 を裏づけた。ヒートシンクの小さいボードの自身の発熱は未確認
- 掲載中のBTO 16件の 2D・3D 比較(`_dev/bto3d.html`)で、VRM は 3D が平均 3.7°C 低い(−14〜+8°C)。風の弱い構成ほど 3D との差が大きい。CPU・GPU の差は約2°C
- 2D では VRM に当たる風が 0.5 m/s より弱いときは 0.5 m/s として扱う(`VRM_V2D_MIN`、sheet-v65-vrm2d)。2D の風速は 3D とほぼ関係がなく、この下限で 2D が 3D に最も近づく。作者のPCの実測とも 2D で −0.1〜+3°C
- 次の候補:掲載中のBTOのマザーボードを製品ごとに登録(案B)、VRM の実測を増やして較正(案C)

## 3D の計算のしかた(2026-10-14)

クラウド側には GPU がないため、3D は作者のPCの内蔵ブラウザ(Claude デスクトップアプリのブラウザ)で計算する。

1. 内蔵ブラウザで `https://sonnet320.github.io/pc-sheet/` を開く
2. 先に保存データ(localStorage の `bto-sheet-v1`)を別のキーに退避する
3. シートの HTML を取得し(作業ブランチなら raw.githubusercontent.com のコミット指定の URL)、最後の `})();` の直前に `window.__dbg=s=>eval(s);` を足して、`<base href="https://sonnet320.github.io/pc-sheet/">` を入れた iframe(srcdoc)で開く。同じページへの document.write は変数が重複して失敗する
4. iframe の中で構成と条件を設定し、`diag2d`(2D)と `Air3D.diag`(3D)を呼んで、`diagEval` で温度を出す
5. ブラウザの画面が隠れていると計算が止まる(requestAnimationFrame が止まる)。始める前に表示してもらう
6. 終わったら iframe を消し、保存データを元に戻して再読み込みする

## 録画モードの作り直し(2026-10-26)

- 2窓で録画した動画をスマホで見ると文字が小さいため、録画モードを作り直した(計算・`DIAG_VER` は変えていない)
- 録画モードでも、構成表の▼(パーツの変更)・2D/3D の切り替え・図のファンの選択と移動ができる。設定のカードは隠したまま
- ステージの下に録画用のパネル(`#recbar`)を出す。おすすめBTO(`config.json` の掲載中の構成を読み込む)・文字の大きさ(標準/大/特大/最大)・並べ方(横並び16:9/縦並び)・終了ボタン
- 負荷(CPUの負荷・CPU/GPU使用率)と、ファン(追加・選んだファンの種類や回転数・削除、全ファンの種類と回転数、パーツごとの価格の表示)は、元の設定カードの部品をパネルへ移して使う(終了すると元の場所に戻す)
- 文字の大きさは CSS の `zoom`(`--fz`)で、構成表・上のバッジ・温度の欄・パネルにかける。図(canvas・3D)にはかけない。文字が大きくて16:9に収まらないときは、ステージが縦に伸びる
- 縦並びは図の高さを画面の約半分にする(`fit()`)。録画モードの設定はブラウザの `pc-sheet-rec-v1` に保存
